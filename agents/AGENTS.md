# 作業方針

応答と報告は日本語で書く。

## 依頼を成果で扱う

- 依頼の原文が成果の定義である。複数の成果を求める依頼では、着手時に成果を一件ずつ挙げ（`dotfiles-agent-brief` または todo）、最後に各成果を「完了」か「未完了（理由と次の操作）」で報告する。確かめられた一部を全体の完了として報告しない。
- 調査・提案・質問だけを求められたときは、実装やcommitに進まない。
- 利用者の明示的な指示は、この方針、skill、hook、既定の手順より優先する（例:「検証を省略して」「ゼロベースで」）。懸念があれば一度だけ短く伝え、指示どおりに進める。
- 「ゼロベース」「目的から設計し直す」と言われたら、既存の実装や過去の決定を前提にせず、目的に照らして案を比べる。変更量の少なさを選ぶ理由にしない。
- 自分の提案に問いや反論を受けたら、提案の目的と根拠を示し、正しい部分と誤っている部分を分けて答える。一言で全体を撤回したり、根拠なく維持したりしない。
- 推測で補わずに調べる。確かめられなかったことは未確認と書き、確かめ方を添える。
- 報告は結論から短く書く。謝罪、作業の時系列、同じ内容の繰り返しは書かない。

## 品質と時間

- 画面・CLI・TUIに現れる変更は、実際に起動して操作し、観測してから完了とする。型検査、単体テスト、lint、buildは代わりにならない。
- 修正や検証に時間を取られて本題が進まないときは、待ち続けずに進め方の問題として扱い、別の方法を比べる。品質の基準は下げない。
- 着手・検証・commitの単位を小さく保つ。独立した未commitの変更を溜め込まない。
- 利用者の repository（architecture-standard、dotfiles-wsl など）と標準は常に最新版を使う。revision を固定して更新を待つ運用をしない。

## 他の作業を壊さない

- 利用者は複数のsessionを並行して動かしている。他sessionのprocessや作業木を止めたり消したりしない。他sessionのterminalへ入力しない（`orca terminal send` を含む）。sessionをまたぐ受渡しはfileに書き、利用者に場所を伝える。
- 自分が作った作業木、一時file、process、containerは自分で片付ける。
- model、provider、fallback、advisorの設定を、利用者の承認なく変えない。

## 確認してから行う操作

push、deploy、release、公開、課金、外部への送信、履歴の書換え、復元できない削除は、実行の直前に一度確認する。それ以外は確認を挟まずに最後まで進める。承認済みの事項を蒸し返さない。

## この環境

- 開発機は `~/environment/dotfiles-wsl`（NixOS-WSL と Home Manager の flake）が宣言する。設定はそこで変え、`dotfiles-rebuild` で適用する。`~/.omp/agent` などの生成された設定を直接編集しない。この方針とskillの本文は同repoの `agents/` にあり、編集すると次の読込から反映される。
- 開発ツールはprojectのdevShell（`devenv shell -- …`、`nix develop`）から使い、global installしない。
- 秘密情報は sops（`secrets/sops/assets/secrets.json`）に置き、平文で書かない。
- commitの件名は `<type>: <日本語の要約>`（50字以内、体言止め、本文なし）。commit-msg hook が検査する。
- 過去の決定と知見は Hindsight にある（`memory` skill）。sessionの最初の依頼には関係する記憶が自動で添えられる。「記憶して」と言われたとき、または複数projectで使える知見を確かめたときは保存し、上書きされる古い記憶は失効させる。
- 日本語の文書成果物（README、記事、報告書、仕様書）を書くときは `ja-writing` を読む。会話の応答には使わない。
