# 統合の評価

外部toolの採用や差替えを、そのtoolを使う環境と一緒に評価する。
結果は、問いに対応する証拠、導入後の呼出し関係、変更の所有者へ渡す契約である。

## 問いと証拠を対応付ける

利用者が知りたい対象と状態を、調査queryや委譲briefを作る前に固定する。
採用候補の名前は調査のanchorにし、質問の対象をその名前の登録有無へ置き換えない。

| 問い | 必要な証拠 | 区別する事実 |
|---|---|---|
| 他toolにも使える配備の仕組みがあるか | package、registry、起動、認証、stateなど該当する契約の定義と、既存の利用箇所 | 候補の登録有無、配備の仕組み、実機での稼働 |
| 現在何が選択、登録、稼働しているか | 選択と登録のsource、必要な場合だけ認可された実状態の観測 | registryの候補集合と採用集合、宣言と実状態 |
| 既存との仕事が重複するか | 既存と候補の呼出し関係と、採用後に更新するcaller | 同じ目的を持つ入口と実装、独立した二重処理、選択可能な実装 |

sourceの所在や関係が不明な部分は、この問いと確認済みanchorを`repository-research`へ渡す。
公開資料が必要な部分だけ`web-research`へ渡す。
返却結果が質問と違う状態や層の証拠なら、結論へ使う前に調査を戻す。
このstepは、各問いに必要な証拠と、その証拠では判定できないことを対応付けた時点で完了する。

## 導入後の呼出しを比較する

環境が宣言する責務境界の正本を読み、既存の入口から実装までの呼出しを、その環境の用語で追う。
Skillや実行担当が外部toolを呼ぶ場合は、その呼出し関係を比較の入力にする。
名称や目的の一致ではなく、誰が何を判断、実行し、どの結果を受け取るかを特定する。

候補ごとに、既存callerを更新した後の呼出しと結果の戻り先を組み立てる。
入口、routing、依存、入力、権限、出力、失敗時の扱いのうち、変わるものと変わらないものをsourceまたは提案として区別する。
関連callerを更新する案と、同じ処理を独立して追加する案を同じ構成として採点しない。
採用済みという状態を既存実装の温存理由にせず、候補が引き継ぐ処理は置換とobsoleteの除去まで含める。

重複とする処理は、更新後も独立して残る所有者と実行経路を示す。
callerと呼び出される実装は合成として扱い、複数候補は代替実装として選べるか、同時利用に別の価値があるかを評価する。
実装の内部にも計画や判断がある場合は、caller側で同じ処理をやり直す範囲と、結果を受け入れる条件を特定する。
このstepは、変更後のcallとreturnがつながり、重複、合成、置換の判断に対応する経路を示した時点で完了する。

## 既存の配備契約へ載せる

共通配備口の評価では、候補が必要とする供給、起動、認証、保存先、資源、通信の条件を、既存の契約へ対応付ける。
利用できる仕組み、owner内で調整する設定、契約自体に必要な変更を分ける。
個別のCLIやAPIの差を、共通配備の仕組みが存在しない証拠にはしない。
利用者が実行Interfaceの統一を求めている場合だけ、その共通化を別の変更として扱う。

調査や採用案の依頼から、install、login、課金、外部送信、service切替の許可を推定しない。
受入条件は実行するstepを持つ契約として示し、未実行の互換性や性能は未確認に残す。

## 所有者へ戻す

候補ごとの判断、証拠、変更後の呼出し、配備契約との差を、主張ごとの変更理由へ戻す。
既存caller、外部実装の供給、runtimeやcredential、配備と検査の更新を、同じ採用案の変更範囲に含める。
本文の「所有者を決める」から再開し、配備口の調査結果を新しいSkillや独自実装の作成理由にしない。
