# 0016. 文書は主張と寿命で分類し、時点に固定される文書は追跡しない

## 状態

Accepted

## 背景

`docs/` は 構築、運用、構成、変更、設計判断、監査 の六つの目的を索引で宣言していたが、ディレクトリは五つで、対応が一対一でなかった。構成は `architecture/` と `reference/tooling.md` に分かれ、変更は root 直下の `development.md` と `reference/change-map.md` に分かれていた。`getting-started.md` と `development.md` だけが root 直下にあり、同じ種類の文書が別の階層に置かれていた。tree を見ても文書体系を説明できない状態だった。

`docs/audits/2026-07-29-tooling.md` は四つの役割を兼ねていた。冒頭で実行順を決定し、外部 repository の集計と稼働 service の実測を記録し、七つの改善案を提案し、維持する構成を判断していた。file 名は日付に固定されているのに、内容は現在も正しくあることを期待されていた。この矛盾から、後日の訂正を同じ file へ後置する運用が生まれ、文書が誤った実測とその打ち消しを同時に持つ状態になった。

`nix flake check` には文書に関する検査がない。そのため `docs/reference/tooling.md` は MCP target 一覧と「10 target」という件数を Nix 宣言から手で転記でき、乖離しても build は成功する。文書の移動によるリンク切れも検出されない。

## 決定

文書を主張と寿命で四つの種類に分け、ディレクトリと一対一にする。

| 種類 | ディレクトリ | 主張 | 寿命 | 変更 |
|---|---|---|---|---|
| 手順 | `operations/` | 利用者が何を実行するか | 常に現在 | 現在に合わせて書き換える |
| 構造 | `architecture/` | 現行 generation が何であるか | 常に現在 | 現在に合わせて書き換える |
| 索引 | `reference/` | どこが正本か | 常に現在 | 現在に合わせて書き換える |
| 判断 | `adr/` | なぜ選び、何を却下したか | 決定時点で凍結 | 状態だけを変え、本文は書き換えない |

`getting-started.md` と `development.md` は手順なので `operations/` へ移す。root 直下に置く文書は索引の `README.md` だけとする。

環境の観測と実装計画は追跡しない。監査は「その日にその機械で何が動いていたか」の記録であり、リポジトリの内容ではない。時点に固定されるため書き換えられず、古くなっても更新できない。実装計画も同じく、完了すれば実装と ADR が正本になる。両方を `.gitignore` へ入れ、file 自体はローカルに残す。`.git/info/exclude` は clone した別ホストへ伝わらないため使わない。

不変記録を後から訂正しない。誤りが判明した場合は、新しい観測を取り直し、判断は ADR へ書く。既存の記録は当時の観測として残す。

文書の主張を検査可能にする。`nix flake check` に link check を加え、文書の移動と参照切れを build で落とす。索引は宣言の値を転記せず、宣言の場所だけを指す。roster や件数を文書へ持たせない。

## 検討した代替案

監査を `docs/` に残し、種類として第五の分類にする案。日付で凍結される文書と、現在を主張する文書を同じ tree に置くと、読み手が現在の正本と過去の記録を区別できない。索引がそれを「改善順序が分かる」と紹介していた実例があるため不採用。

監査から提案と判断だけを取り除き、実測記録として追跡し続ける案。実測は外部 repository の件数と稼働 process の値であり、リポジトリの内容から導けない。commit しても再現できず、検査もできないため不採用。

`.git/info/exclude` を使い続ける案。これはローカル設定であり、同じ dotfiles を使う別ホストでは追跡対象に戻る。分類の規約がホストごとに変わるため不採用。

## 影響

`docs/` の tree が文書の種類をそのまま表す。文書を追加するとき、置き場所は主張と寿命から決まる。

`docs/audits/` と `docs/superpowers/` は追跡対象から外れる。過去の監査は git 履歴に残るが、現在の正本ではない。監査の結論のうち採用したものは ADR、実行順は計画が持つ。

link check により、文書の移動は参照更新を伴わない限り build で落ちる。索引から転記を排除するため、roster の更新漏れという故障モード自体がなくなる。
