# Design it twice

最初に思い付いたinterfaceが最良とは限らない。interfaceの形が実際の判断であり、実質的に異なる案があり得るときに、二案以上を作って比べ、一案を推薦する。
[SKILL.md](../SKILL.md)の語彙と、seamを置く三つの入力を使い、依存の性質は[deepening](deepening.md)で分類する。

## 1. 問題を示す

案を作る前に、利用者へ次を示す。

- 新しいinterfaceが満たす制約
- 頼る依存と、その性質
- 制約を具体にするための粗い素描。提案ではない

利用者が読む間に、続く作業を進める。

## 2. 独立した問いを決める

案は、隠す決定、権限、状態の寿命の置き方が異なることで分ける。名前や綴りだけの違いは別の案にしない。
その設計で決めるべき問いを挙げ、互いに独立で、答えが選ぶinterfaceを変え得るものだけを残す。
例は、何を隠すか、権限をどこに置くか、状態の寿命を呼出し側にどう見せるか、最も多い呼出し側の既定の使い方、seamを越える依存の受け取り方である。
残った問いごとに視点を一つ立てる。視点の数は問いが決めるので、固定しない。残る問いが一つなら、その問いに対する異なる答えを二案作る。

## 3. 案を作る

視点ごとに、その視点の制約だけで案を作る。他の視点の案は見せない。
独立した実行者(subagent)を使うのは、視点が互いに独立で、一つの案が他の案を引きずると比較にならず、実行者を起動でき、費用に見合う場合である。
実行者ごとに別の技術briefを渡す。file path、結合の詳細、依存の性質、seamの背後にあるもの、担当する問いと制約を含め、projectの`GLOSSARY.md`の語彙も添える。
実行者を起動できない場合、または独立性が要らない場合は、視点ごとに順に、その視点の制約だけで案を作り、独立実行ではないと結果に書く。独立性が判断に必要なら、必要な視点とbriefを呼出し元へ返す。
実行者が作った案の比較と推薦は呼出し側が行い、実行者へ再委譲しない。

各案は次を返す。

1. interface(型、method、引数、不変条件、順序、失敗の形)
2. 呼出し側の使用例
3. seamの背後に隠すもの
4. 権限と状態の寿命の置き方
5. 依存の扱いとadapter([deepening](deepening.md))
6. trade-off。leverageが高い箇所と薄い箇所

隠す決定、権限、寿命の置き方が同じ案は一案にまとめ、見かけの差を増やさない。

## 4. 比べて推薦する

案を順に示し、depth(interfaceにおけるleverage)、locality(変更が集まる場所)、seamの位置、権限と寿命の置き方で対比する。
そのうえで最も強い案を推薦する。複数の案の要素がよく組み合わさるなら、混成案を提案する。
利用者が求めるのは強い読みである。選択肢の一覧で終えない。
