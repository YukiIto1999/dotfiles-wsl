## 必須制約

親の session にも subagent にも適用する。

### 実装の着手・委譲・再開

- 機能追加では、処理を起こす操作やイベントから結果までをコードで辿り、どこで何を決めるかを選ぶ。今の実装がその責任を持てるならそこで直す。同じ業務判断を別の入口にも書き足すことになるなら、判断を一か所に置き、関係する既存の呼び出し元もそこへ切り替える。値を保存する前に、既存の事実から導けるか、保存しないと失われるかを区別する。表示だけの変更なら、無関係な状態や構造には手を広げない。
- 別々に受け入れられる成果が複数ある実装、または担当をまたぐ実装では、作業に分ける前に、原依頼の各成果を一件ずつ登録する。プロジェクトに原文・各成果・未達を保持する既存の案件票があればそれを使う。なければ `dotfiles-agent-brief new '原文の参照' '成果1' '成果2'` の返す案件IDを作業計画に残す。工程名は成果の代わりにならない。単発の質問や一人で完結する単一成果の修正に案件票は作らない。
- 親は各作業に担当する成果の番号を付け、担当の決まらない成果も未達のまま持つ。追加依頼は `add`、担当・次の操作・阻害要因は `note`、観測した結果は該当番号だけ `accept` に記す。利用者が撤回した項目だけを、その発言を根拠に `withdraw` する。子の作業完了を他の番号へ波及させない。
- 委譲・再計画・中断では、案件票（`dotfiles-agent-brief show ID`）から、担当範囲、原文の参照、未達と次の操作を渡す。再開時は同じIDを開き、原依頼とその後の採用・撤回、証拠の現物を照合してから未達を選ぶ。IDを失った場合は `list` で原文が一致する案件を探し、最新の一件を推測で選ばない。既存の引継ぎメモしかなければそれを索引に原文から復元し、同じ状態を二重に転記しない。別の作業木にある同名ファイルや日付の新しい草案は決定の根拠にしない。
- 以前の合意に基づく仕事では、案件票の有無によらず、要約より当初の依頼と利用者が採用・撤回した決定の原文を優先する。中断や圧縮をまたぐ際は案件IDまたは既存の作業記録（慣行がなければ追跡外の `work/`）を残す。受け手に開けない私的な発言は、許可された決定の該当部分だけを共有する。会話全文や資格情報を案件票・委譲先へ送らない。決定が食い違う場合は、それに依存する項目だけを保留する。
- 納期か途中報告の約束がある仕事では、着手・再開時と見込みが変わった時に時計を見る。残る必須の受入までの時間には、並行できない統合・検証・配備とその待ちを含め、同じ経路の実績があれば使う。納期から逆算した最終着手時刻と約束した報告時刻の早い方を、利用者に判断材料が届く期限とする。そこから状況の取り直し、判断、送達に要する時間を差し引いて、自分が待機から戻る時刻を決める。所要時間が読めなければ期限ぎりぎりまで待たず、判明した範囲を前倒しで届ける。長い処理は止めず、前倒しした時刻に一度だけ自分のsessionに届く非同期通知か、そこまでの待機を使う。作業完了時は不要になった通知を取り消す。
- 間に合わない見込みになった時点、または判断時刻になっても見通しが立たない時点で、処理の終了や利用者の催促を待たずに、届くもの・届かないもの、根拠となる実績と残り時間、利用者がまだ選べる対応を伝える。仕様・品質を独断で削らず、判断待ちでも独立した作業は進める。期限も報告の約束もない仕事に時刻の台帳やタイマーは設けない。

### 完了の報告

- 実測していない結果を完了として書かない。実行した確認の結果と、失敗したコマンドや未確認の前提を隠さずそのまま報告し、誤りに気づいた時点で訂正する。原版Skillの検証表示は実行範囲の証拠であり、未観測のexit、stream、業務結果を補わない。余分な検証手順は足さない。
- 画面、CLI、TUI に現れる変更は、実際に起動して操作し、観測した結果を証拠として示すまで完了としない。型検査、単体・結合 test、lint、build は起動の代替にならない。起動できない事情があるときは完了と書かず、何を起こせなかったかと未検証である旨を述べる。

### 資源

- 編集中は変更箇所の focused check、高コストな最終確認は `dotfiles-agent-verify -- COMMAND [ARG...]` を使う。上限付きの前景枠がある host で利用者が待つ重い build は `dotfiles-capped-run` に CPU 上限と入場・走行の期限を指定する。配備は `@dotfilesDir@/docs/operations/rebuild.md` に従い、候補準備と中断できない適用を分ける。
- それ以外の高コストな処理は `dotfiles-workload-run --seconds N -- COMMAND [ARG...]` で実行する。入場待ちと走行にはそれぞれ N 秒の枠がある。未起動や取消は監督器の診断で判別し、終了値だけで同じ処理を投入し直さない。資源待ちの確認は `@dotfilesDir@/docs/operations/doctor.md` に従う。同じ条件で成功した検査は繰り返さない。
- `nix build` は明示した out-link が必要な場合を除き `--no-link`、`nix-build` は `--no-out-link` を使う。agent runtime の shim を絶対 path で迂回しない。
- managed runtime wrapper を持つ client では、agent runtime が `TMPDIR`、共有の `CARGO_HOME` と `XDG_CACHE_HOME`、checkout ごとの Cargo の build-dir を割り当てる。利用者が明示した値は空文字列も含めて変更せず、project が明示する Cargo の `target-dir` と `build-dir` も上書きしない。session ごとの cache を `/tmp` に作らない。一時的な写しで build する tool を扱うときと割当の例外は、`@dotfilesDir@/docs/architecture/ai-tooling.md` の cache 方針に従う。
- 自分が起動した server、container、background process と作成した一時資源を作業中に把握し、終了時に自分の所有物だけ停止、回収する。既存物や所有者不明の資源を削除しない。

### 配備物、資格情報、Git

- dotfiles が配備・管理する設定ファイル（生成済みの rules、Skill、subagent、client config を含む）は直接編集しない。変更は dotfiles 内の正本に行う。
- パッケージマネージャでグローバルインストールしない。パッケージは nix / devenv で導入する。
- `gh auth login` / `gh auth switch` は使わない。
- 資格情報を平文に書かない。
- repository の hook を信頼する `git config dotfiles.hooks.trusted true` は利用者だけが設定する。agent は信頼を与えず、repository 側で `core.hooksPath` を上書きしない。
- commit と push の hook を迂回しない。`--no-verify` と、push 前の検証を省く `DOTFILES_VERIFY_PUSH_BYPASS` は利用者だけが使う。hook が失敗したら原因を直すか、直せない事情を利用者へ報告する。
- commit を作る前と件名を求められたときは `commit-writing` を読み、全repository共通の形式と、同Skillが参照する正本の規則に従う。本文・検査・参照更新を 1 つのコミットに閉じ、未検証の中間コミットを残さない。
