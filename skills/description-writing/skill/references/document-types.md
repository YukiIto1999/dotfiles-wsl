# 文書別の判断

## README

最初の読者が対象を識別し、採用可否を判断し、次の正しい入口へ進める内容にする。目的、対象、主要能力、最短の開始点、詳細文書への導線を優先する。内部構造の網羅表にしない。

## ADRとdecision record

構造へ影響する決定について、当時のcontext、比較した選択肢、decision、consequenceを残す。commitの直接目的で代用しない。置き換える場合は過去の記録を消さず、supersededを示す。

## 仕様

実装案でなく、外から観測できる契約、不変条件、状態、失敗、境界、acceptance criteriaを明確にする。未決定事項と決定済み事項を分ける。

## 手順

前提、開始状態、順序、分岐、成功条件、失敗時の再開方法を書く。
OS、shell、runtimeとtoolのversion、作業directory、必要な権限を明示し、作者のhelperやdotfilesを暗黙に使わない。
code、config、sample入力を記事に含めるか、読者が取得できる固定revisionの入口を示す。
placeholderには値の決め方と秘密情報の扱いを添え、commandの期待exit、stdoutとstderr、確認する生成物または状態を区別する。
危険な操作は対象と影響を先に示し、背景説明を途中へ挟まない。
これは執筆する内容の契約であり、実行や再現性の判定は`article-reproduction`へ渡す。

## 参照

既知の項目を速く引くための正確な索引にする。説明を混ぜず、正本と現在値の取得方法を指す。手で同期する値を増やさない。

## 報告と提案

観測した事実、解釈、推奨、未確認事項を分ける。推奨は制約と比較理由を持たせる。調査量を成果として列挙しない。

## Onboarding

読む順番を、参加者の最初の仕事と入口から決める。
既存の用語集を参照し、未確定の業務語をsourceの名前だけで定義しない。
domain用語の確定と用語集の変更は`domain-modeling`へ渡し、実装上の名前、repositoryの責務、技術構成は説明として分ける。
必要な実装mapには、その記述を直接支えるsource locatorとrevisionを添え、証拠がある関係だけを図にする。
固定したfile集合やdiagram数のために文書を増やさない。
